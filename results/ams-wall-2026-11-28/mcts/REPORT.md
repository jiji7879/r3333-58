# Current-generic AlphaMapleSAT on the exact K58 wall row

## Result

**The previously unrun `rollout-extra=20`, two-simulation wall configuration was executed. It emitted exactly the same four-leaf tree as shallow two-simulation MCTS, byte for byte, and all four fresh leaves remained OPEN at the same $10^6$-conflict cap.** No SAT or UNSAT verdict follows.

This is more than a timeout observation. Current `MCTS.py` has a concrete two-simulation limitation at a fresh root: the first simulation only initializes the root policy and returns; the second expands one literal and its complement, evaluates their two immediate nonterminal children, and returns. It cannot reach the nominal 20-step terminal horizon. The actual wall log printed `WARNING:MCTS:NO EXPLORATION!!!!`, and a toy-game execution of the unmodified current `MCTS.py` confirmed depth 1 for both terminal horizons 2 and 22. Thus this run must not be presented as a genuine deep root rollout experiment.

There is **no independently checked faster/easier decomposition and no proof or physical-colouring closure**. The result is a scoped structural negative result for the current two-simulation interface, not a theorem that deeper MCTS, more simulations, or another policy cannot help.

## Why the attempted route failed structurally

At commit `215224b…`, `MCTS.search` handles a state with no `Ps` entry by initializing `Ps` and returning `canonicalBoard.total_rew`; it does not select an action on that visit. At a fresh root with `numMCTSSims=2`:

1. simulation 1 initializes the root and returns at depth 0;
2. simulation 2 selects one action, initializes **both immediate child states**, returns their nonterminal values, and updates `Bsa` only for that action and its complement;
3. `getActionProb(temp=0)` chooses by maximum `Bsa`, and exactly one literal/complement pair has nonzero root visits—the state guarded by the actual `NO EXPLORATION` warning.

Hence a terminal test at emitted-depth-plus-20 is never reached at that root. This is a property of the current expansion logic, not an inference from the wall timeout. It explains why changing `rollout-extra` cannot by itself turn the two-simulation root choice into a deep rollout. Lower states may have prior cache entries, so this argument is scoped to a fresh root; empirically, the wall's two second-level choices also remained 1014 and 1417.

The executable control `scripts/mcts_horizon_control.py` uses the actual unmodified `MCTS.py`, with prior-action paths distinguished as in `KSGame.stringRepresentation`. With terminal horizons 2 and 22 it observed, in both cases:

```json
{"terminal_test_depths":[0,1,1],"expanded_depths":[1,1],"max_depth_reached":1,"root_visit_count":1,"selected_actions":[1]}
```

Control receipt: `results/mcts-horizon-control.json`. This is a control-flow test only, not a CNF or colouring verdict.
